# 备份与恢复

## 备份

`./tools/backup.sh` 把 `data/` 打包成带时间戳的 tar.gz 到 `backups/`（`BACKUP_DIR` 可改）：

```bash
BACKUP_DIR=/var/backups/kbai BACKUP_KEEP=14 ./tools/backup.sh
```

- **SQLite 一致性**：app.db 用 `VACUUM INTO` 快照（不是热拷贝），避免拷到 WAL 中间态。
- **覆盖范围**：`app.db`（业务库）、`documents.json`（知识库）、`policy.json`（权限）、
  `config.json`（敏感词/人名等）、`secret.key`（会话签名）、`entities.json`（记忆）、
  `oauth_state.json`（OAuth 客户端/令牌）、`auth_users.json`（账号，如存在）。
- **权限**：产物 `0600`。
- **保留轮转**：`BACKUP_KEEP`（默认 14）份，超出的自动删除；跨主机至少一份异地/对象存储。
- 建议放到 cron：`30 2 * * * /path/enterprise-ai-assistant/tools/backup.sh`。

> embeddings_cache.json（向量缓存）可重建、体量大，默认**不备份**；丢失只会触发重新向量化。
> 审计日志本身有 `AUDIT_MAX_BYTES`/`AUDIT_BACKUPS` 的轮转；如需归档到备份盘，
> 把受管目录（如 `/var/log/kbai/`）加入备份脚本的外部 tar 即可。

## 恢复演练（先在小环境练一次）

```bash
# 1. 停下相关服务（避免 db/状态文件被你写的半中间态覆盖）
pkill -f "mcp_servers/"; pkill -f start_all.sh || true

# 2. 备份当前疑似损坏的 data/，再解包恢复
mv data data.corrupt
mkdir -p data
tar -xzf backups/kbai_data_<时间戳>.tar.gz -C data/

# 3. 校验关键文件
test -f data/app.db && test -f data/documents.json && test -f data/policy.json
sqlite3 data/app.db "PRAGMA integrity_check;"        # 期望 ok

# 4. 重启并验证
./start_all.sh & sleep 12; ./check_servers.sh
curl -s http://127.0.0.1:8000/healthz

# 5. 抽验「已授权客户端仍可用」「能检索到文档」——命中即恢复成功
```

要点：
- 恢复 `oauth_state.json` 后，已授权客户端/令牌仍有效，**用户不需要重新走一遍浏览器授权**。
- 恢复 `secret.key`（会话签名）避免 Web 会话集体失效；勿用旧盘里过期备份覆盖新的 key，
  以免丢弃后续会话。
- 恢复 `app.db` 后，工单/请假编号从备份点位继续（AUTOINCREMENT）。

## 什么需要你手动补

- **审计日志归档**：受管目录的轮转文件（`.1/.2`）不在 `data/`，需在备份脚本外自行 tar。
- **TLS 证书**（若应用层 HTTPS）：证书/私钥在系统路径，纳入系统级备份。
- **`/etc/kbai/connector.env`**：环境变量文件不落库，须单独备份（含权限 600）。
